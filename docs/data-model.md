# Модель данных

Движок предметно-нейтрален. «Донхуа», «рыбалка», «книги» существуют
только как данные пользователя — в схеме их нет и быть не должно.

## Объекты

Одна таблица `objects` на три роли:

```
entry (parent_id IS NULL)
 ├── attachment  ──── note
 ├── note
 └── ...
```

У любого объекта могут быть свойства (`properties`) и теги (`object_tags`),
поэтому «тайминг у скриншота» работает без единого изменения схемы —
это обычное свойство обычного объекта.

Глубину ограничивает приложение (`entry → attachment → note`), схема
допускает больше. Если понадобится — ограничение снимается без миграции.

## Свойства

EAV с **типизированными колонками значения**: `value_text`, `value_num`,
`value_date`. Ровно одна заполнена, что гарантирует CHECK.

Один общий `value TEXT` был бы ловушкой: `rating>=9` сравнивал бы строки и
`'10'` оказалось бы меньше `'9'`. Даты — ISO-8601 UTC в TEXT: такой формат
сортируется лексикографически, отдельного числового поля не нужно.

`key_norm` (lower от `key`) существует ради фильтров вида `озвучка:anistar`
при том, что пользователь видит своё написание — «Озвучка».

## Коллекции

Связь `object_collections` — many-to-many. Запись «Противостояние святого»
одновременно лежит в «Донхуа», «Любимое» и «Топ-10» без копий.

Приложение требует минимум одну коллекцию у записи; схема этого не
навязывает.

## Поиск

Два независимых уровня, они не смешиваются:

**1. Полнотекстовый — FTS5.** Одна строка `search_index` на объект.
`content` — склейка `title`, `body`, ключей и значений свойств, имён тегов,
`caption` вложения.

**2. Структурный — обычный SQL** по `properties` / `object_tags` /
`object_collections`. Именно здесь живут `rating>=9`, `episode>100`,
`has:image`, `status:watching`.

Комбинированный запрос = пересечение `object_id` из обоих уровней.

### Разрешение результата в карточку

FTS находит **любой** объект, в том числе заметку и вложение. Найденное
надо поднять до корневой записи, но показать место попадания —
пользователь ищет «Ван Линь» и должен попасть на конкретный скрин, а не
просто на карточку. Глубина фиксированная, поэтому хватает двух `LEFT JOIN`
вместо рекурсивного CTE.

### Синхронизация индекса

Триггеры **не** пересобирают `content` — на чистом SQL это хрупко и
дорого. Они лишь кладут `object_id` в очередь `search_dirty`. Приложение
разгребает очередь тем же `db.batch()`, что и саму запись; cron подчищает
хвосты, если воркер упал между операциями.

Актуальный запрос пересборки — `REINDEX_SQL` в
[search.ts](../src/infrastructure/d1/search.ts).

### Значения в индекс кладутся отформатированными

Сырые колонки в индекс писать нельзя. Тайминг хранится как `754`
секунды, дата — как `2026-07-01T00:00:00Z`, а ищет человек `12:34` и
`01.07.2026`. Поэтому при индексации значение приводится к тому виду, в
котором его ввели: `duration` → `12:34`, `date` → обе формы сразу,
`bool` → `да`/`нет`, `number` → без хвостового `.0`.

Это ловушка, которую видно только на живых данных: индекс наполняется,
запросы не падают, просто ничего не находится.

### Ещё одна ловушка: bm25 и планировщик

`bm25()` и `snippet()` работают только там, где запрос обращается к
FTS-таблице напрямую. Обычного подзапроса недостаточно — планировщик
схлопывает его во внешний JOIN, и запрос падает с
`unable to use function bm25 in the requested context`. Спасает
`WITH fts AS MATERIALIZED (...)`: материализация запрещает схлопывание.

### Ограничение, которое надо помнить

Токенайзер `unicode61` не знает морфологии: **«карась» не найдёт
«карася»**. Для MVP приемлемо; лечится префиксным индексом
(`prefix='2 3 4'`) или нормализацией слов при индексации — но это уже
осознанное решение, а не забытая деталь.

## Состояние диалога

На Workers нет памяти между запросами. Любой пошаговый мастер
(«Название поля?» → «Значение?») живёт в `user_state`, иначе он
развалится на первом же холодном старте. Это не оптимизация, а
обязательное требование среды.

## Медиа

Храним только идентификаторы, файлы остаются у Telegram:

- `file_id` — для повторной отправки. **Привязан к токену бота**: при смене
  токена все `file_id` становятся мусором, и восстановить их неоткуда.
  Это единственная реальная точка невозврата в дизайне — токен беречь.
- `file_unique_id` — стабильный, годится для дедупликации, но отправить
  файл по нему нельзя.
